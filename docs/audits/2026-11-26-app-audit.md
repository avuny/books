## 0. Scope and limits

Covered: sign-up with email OTP, organization creation, customers, vendors, unit collections, item categories, items with opening stock, warehouses and locations (read), inventory adjustment confirm flow, stock movements (item ledger), roles (system and custom), invitations (send), user menu, sidebar.

Not covered (browser was slow, 30 to 70 seconds per action): invitee login and the accept-invite flow, permission enforcement for a restricted role (UI hiding vs API 403), unit create/edit, warehouse and location create, organization settings save, forgot-password, sign-in error states, Arabic/RTL, mobile viewport, stock-movement page filters, role edit, member deactivation. These are listed in the testing plan as first e2e targets (docs/TESTING-PLAN.md).

Test data created in the live database, to clean up: users `khaledaliskandrani+avunyqa1@gmail.com` and `+avunyqa2@gmail.com`, org "QA Trading Co" (slug `qa-trading-2`), orphan org slug `qa-trading-co`, customer "Nile Retail LLC", vendor "Delta Supplies Co", item "Widget A" (100 units opening stock), role "Sales Clerk", one pending invitation.

## 1. What is good

- Sign-up with email OTP works end to end. OTP email arrives fast, org creation follows.
- Clear modular structure: contracts first, route/feature split, per-module locales, generated API client. The repo's own docs (AGENTS.md, `.agents/` rules and skills) are unusually strong for AI-agent work.
- Customers and vendors on one Party model, with nested "create inline" dialogs. Creating a customer or vendor was smooth.
- Item ledger: the stock movement for the opening stock is written and shown on the item.
- Inventory adjustment confirm dialog wording is clear about what will happen.
- Invitations page and invite email send work. Role model has sensible system roles (Administrator, Team manager, Viewer) plus custom roles.
- Test setup is realistic: real test Postgres, per-test tenants, OTP capture. CI already runs integration and e2e jobs.

Severity: S1 blocks a core flow or corrupts data, S2 wrong behavior with a workaround, S3 cosmetic or polish.

## 3. What should be enhanced

- Make every multi-step write atomic. Preferred: switch to a transaction-capable driver (Neon WebSocket pool or Hyperdrive), as the SaaS spec fixes plan already proposes (D1). Until then add compensation and idempotency keys for create-item-with-opening-stock and create-organization.
- Map every domain error code to a localized, human message. Never render a raw key, DB constraint name or enum.
- First-run onboarding for a new organization: a checklist (set currency/timezone, add a unit collection, a category, a warehouse, the first item, invite a teammate). Seed default unit collection and category.
- Item form: tracking type control (none, batch, serial), expiry, inline create for category and unit. Default tracking to none.
- Item and inventory views: per-location stock table, reserved/on order/in transit columns (needed by the sales and purchasing specs), cleaned decimals by unit precision.
- Roles: show permission counts, group labels from locale files, a "what can this role do" summary, and a test-as-role preview.
- Members: last active, role change, deactivate, resend and revoke invitation, expiry shown.
- User settings: password change, language, notification preferences, sessions.
- Lists: sorting, filters, empty states with a primary action, bulk actions, export.
- Quality: error boundary and 404 with layout, document title per route, aria-labels, focus management in dialogs, RTL check for every screen.
- Observability: request id on every API error shown to the user, structured logs, an error tracker on web and worker (see docs/FEATURE-TRACKING.md).
